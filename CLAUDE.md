# Project: walkthrough-lib

## What this is
An open-source, framework-agnostic JS library for guided in-app product walkthroughs.
It shows a spotlight + tooltip on a real DOM element and waits for the *actual user* to
click it before advancing to the next step (not an auto-playing video, not a passive
animation — the user performs the real action in their real product).

Think: a lighter, better-designed alternative to Shepherd.js / Intro.js / driver.js,
with two things they lack:
1. Flows can be generated by capturing real DOM click events (not hand-written only).
2. Steps store multiple fallback selectors so a flow survives minor UI changes.

## Core principles — do not violate these
- **No AI, no API keys, no network calls required for the core library to work.**
  The player and the capture tool must both work 100% offline with zero dependencies
  on any AI service. AI (for tooltip copy generation) is an optional *add-on* layered
  on top later — never a requirement.
- **No video, ever.** "Capture" means listening to real DOM click/input events and
  recording selector data (id, aria-label, text, css path) — not screen/video recording.
  Never build or suggest a video-recording or video-analysis feature.
- **Deterministic over guessed.** Element matching tries a ranked list of selectors in
  order (see docs/SPEC.md). Never do fuzzy visual/ML guessing in the core library.
- **Flows are plain JSON files that live in the developer's own repo.** No hosted
  backend, no database, no accounts required to use the library. Think "OpenAPI spec,
  not a SaaS dashboard."
- **Zero dependencies in the core package.** Pure TypeScript + DOM APIs only. Framework
  wrappers (React, Vue) are separate optional packages that depend on the core.

## Scope discipline (read this before writing code)
This project has a documented tendency to scope-creep into a 6-month rebuild. To avoid
that: **only work on the single active step in docs/ROADMAP.md.** If you think a task
needs something from a later step (AI copy generation, the capture tool, self-healing
matcher, React wrapper, editor UI) — stop and flag it instead of building it early.

## Tech stack
- TypeScript, compiled to plain JS (ESM + CJS output)
- No runtime dependencies in the core package
- Vanilla CSS with CSS custom properties for theming (no CSS-in-JS, no Tailwind dependency
  in the library itself — consumers shouldn't need a build step to use it)
- Package manager: npm
- Testing: vitest (add when we reach a step that needs it — not required for Week 1)

## File/folder conventions
- `src/` — library source
- `src/types.ts` — the Flow/Step schema (see docs/SPEC.md — keep these in sync)
- `src/player.ts` — the replay engine
- `src/capture.ts` — DOM event capture (build later, not yet)
- `src/react/` — optional React wrapper (build later, not yet)
- `examples/` — standalone HTML demo pages used for manual testing, not part of the
  published package
- `docs/` — reference docs (this folder), not published to npm

## Definition of done for any step
Code that compiles, a manual test in `examples/demo.html` that visibly works in a
browser, and nothing built beyond what the current roadmap step asked for.
